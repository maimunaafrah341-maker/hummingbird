# HazardWatch OS

A camera watches a bay. Somebody walks in without a hardhat. Nobody
presses anything.

A few seconds later there is an open incident, a spoken warning in the
language of the person standing there, a PDF an inspector could sign,
and an SMS on the safety officer's phone. If nobody acknowledges it,
the system escalates on its own.

That last sentence is the project. Detecting a violation is a model
call; *acting* on one with no human in the loop is a series of
decisions about when **not** to act, and that is where almost all of
this code lives.

---

## See it work in 30 seconds, with no camera

```
pip install -r requirements.txt
pip install reportlab pyttsx3 gTTS playsound3

python smoke_test.py incident
```

This runs the real trigger, the real incident service, the real PDF
writer and the real dispatch layer against local stubs. It never
imports ultralytics, so it needs no camera, no GPU and no model
download. It speaks out loud and writes a PDF to `outputs/`.

Two more, each proving the opposite thing:

```
python smoke_test.py suppressed   # the system declines to act, and says why
python smoke_test.py escalation   # the system acts without being asked
```

## The path one incident takes

```
  camera frame  --+
                  +-->  confidence_router --> TriggerGate --> fire_incident()
  kiosk button  --+          two tiers         3-of-8 +            |
                                               cooldown            |
                                                                   v
                                                          POST /incident
                                                          (incident_api.py)
                                                                   |
                     +----------------+---------------+------------+
                     v                v               v            v
               alert_language     tts_alert       dossier.py   webhook_dispatch
               translate the      speak it        PDF report   SMS / Telegram
               spoken line        out loud        to outputs/  / Slack
                                                                   |
                                                                   v
                                                          escalation_watcher
                                                          no ack in N seconds?
                                                          escalate by itself
```

The camera and the kiosk button meet at **one** function. Nothing
downstream can tell them apart except a `source` field that is recorded
and never branched on — because a fallback that runs different code
from the thing it replaces is not a fallback, it is a second bug
surface.

## The four decisions worth defending

**1. A detector is not a trigger.**
YOLO re-decides the world 30 times a second. Wired straight to POSTs,
one person without a hardhat generates 30 incidents per second. Two
independent gates sit in between: a violation must appear in **3 of the
last 8 frames**, and once fired it is muted per zone for a cooldown
window. Measured: one minute of continuous violation is **1800
detections in, 2 incidents out** — 99.9% suppressed, at 2.7 µs per
frame. The thing that prevents the flood is far cheaper than a single
inference.

**2. Confidence is evidence, not a boolean.**
A `NO-Hardhat` box at 0.92 and one at 0.47 are different claims.
Measured violation-class precision is 0.827, so roughly one in six
detections is wrong — and the wrong ones cluster near the floor. So
detections above 0.75 fire immediately; between 0.45 and 0.75 they
enter a verify state and must be reconfirmed before anything happens.
Ones that never reconfirm are logged as suppressed false positives with
a reason, not discarded silently.

**3. The dangerous output is never generated by a model.**
`/incident` answers from a deterministic rules table. Severity, the
response steps and — above all — the **contraindication** ("do not add
water to the acid") come from that table and never from an LLM. A model
that invents a contraindication is the one failure mode this system
cannot have. The regulatory citation is either supplied by the service
or matched against a local table of real 29 CFR standards, and the PDF
always prints **which of the two** it used.

**4. It escalates when nobody is listening.**
The worst case is not a missed detection. It is everything firing
correctly into an empty bay. A HIGH incident starts a daemon timer; no
acknowledgement inside the window produces a *different* webhook
(different channel, tagged `ESCALATED — NO ACK`), an addendum page
merged into the existing PDF, and the alert re-spoken with reworded
urgency. Never a resend, and never blocking — the camera keeps watching
the bay while the clock runs.

## Bay Twin — watching it decide

```
python bay_twin.py --live demo-01-best-13386074.mp4
```

One command: it starts the incident service, opens the floor plan, and
runs the real detector against that footage. **Nothing on the page is
scripted or seeded** — the floor starts empty and a bay appears the
moment it reports something. Measured on that clip: 242 routing
decisions and 3 incidents in the first 45 seconds, every one produced
by the real modules.

A live top-down view of the floor. Red tile: an incident is open, with
the acknowledgement window counting down on the tile itself. Black tile:
nobody acknowledged it and the system escalated on its own.

**Amber dot: a borderline detection was held, and then suppressed.**

That third one is why the page exists. A red tile is YOLO working, and
every team in the room has one. An amber dot appearing, hesitating and
fading out is this system *deciding not to cry wolf* — the part that
took the work and the part that is otherwise invisible in a terminal.

Live footage produces several decisions a second, so the trail has a
**Key / All** toggle. Key hides the routine holds and reconfirmations;
the counters count everything either way.

Two other ways in. `python bay_twin.py --demo` runs a scripted stream
with no camera and no model — the version that cannot fail on stage.
And if the service is already up, point the trigger at it by hand:

```
python yolo_trigger.py camera --zone BAY-3 --api http://127.0.0.1:8001 \
    --twin http://127.0.0.1:8001 --source demo-01-best-13386074.mp4
```

Then open <http://127.0.0.1:8001/twin>. The `--twin` flag is telemetry
only: the emitter is fire-and-forget on its own thread with a bounded
queue that **drops rather than waits**, and it swallows every error. A
twin that is not running, a browser that stops reading, a network that
drops — none of them can slow down or fail a detection. If the
dashboard breaks, the system keeps working and simply is not being
watched.

## Measured, not claimed

Two reports, both regenerated by running the code. No number in either
is an estimate, and anything that could not be measured says so.

| | Report | Regenerate |
|---|---|---|
| Behaviour, latency, memory | [EVAL-TRIGGER.md](EVAL-TRIGGER.md) | `python eval_trigger.py` |
| Detection accuracy | [EVAL-ACCURACY.md](EVAL-ACCURACY.md) | `python eval_accuracy.py --data <data.yaml> --split test` |
| The language service | [EVAL.md](EVAL.md) | — |

**152 of 152 checks pass**, across ten suites, each running as its own
process so none of them can pass on state another one left behind.

Accuracy, on the Roboflow Construction Site Safety test split
(82 images, 687 labelled instances):

| | Value |
|---|---|
| mAP@50, all classes | 0.708 |
| Precision, violation classes | 0.827 |
| **Recall, violation classes** | **0.539** |
| Weakest — `NO-Hardhat` recall | **0.477** |

Quote the bottom two rows, not the top one. The trigger acts on `NO-*`
classes and nothing else, so a headline mAP that averages in `vehicle`
and `machinery` is not the number to judge this system by.
`NO-Hardhat` misses roughly half of true instances — which is exactly
why the gate is 3-of-8 rather than 5-consecutive, a threshold that
recall figure would almost never clear.

`eval_accuracy.py` refuses to run unless the dataset's class names match
the model's **index for index**. Ultralytics compares classes by index
and never checks the names, so a mismatched dataset silently scores
`NO-Hardhat` against `Safety Vest` and returns a confident, meaningless
number.

Speed, CPU only, no GPU:

| | |
|---|---|
| Live camera path — capture, infer, gate | 47 ms (21.2 fps) |
| Time to fire | 0.1–0.2 s |
| PDF dossier | 16 ms |
| TTS cache hit vs cold synthesis | 0.72 ms vs 4.81 s (**6700×**) |

That last row is why every alert is cached to disk by (text, language).
A demo in a bad-wifi room, in Hindi, is the case that breaks otherwise.

## The modules

Every one of them runs standalone and proves itself —
`python <module>.py --selftest` (`python yolo_trigger.py selftest`,
without the dashes), and most take a `--demo` too.

| File | What it is |
|---|---|
| `yolo_trigger.py` | The autonomous half. Camera and kiosk paths, `TriggerGate`, evidence capture, async downstream dispatch, `doctor` pre-flight. 20 checks. |
| `confidence_router.py` | Two-tier confidence. HIGH fires, BORDERLINE verifies or is suppressed with a reason. 14 checks. |
| `escalation_watcher.py` | Escalates an unacknowledged HIGH incident. Distinct webhook, PDF addendum, re-spoken alert. 19 checks. |
| `bay_twin.py` | The live floor plan. Event bus, SSE stream, and a single self-contained page with no CDN. 26 checks. |
| `incident_api.py` | `POST /incident` — deterministic rules for severity, steps and contraindication. Plus `POST /incident/brief`. 12 checks. |
| `tts_alert.py` | Server-side speech. Offline via pyttsx3, gTTS for hi/bn/te/ur, disk cache keyed by (text, language). 8 checks. |
| `alert_language.py` | The seam between the two halves. Never returns text tagged as a language it is not actually in. 7 checks. |
| `dossier.py` | The PDF. Contraindication in a red box **above** the steps, evidence frame embedded, citation source named on the page. 15 checks. |
| `webhook_dispatch.py` | SMS / Telegram / Slack payloads, per-channel formatting, delivery report, and a local stub receiver. 17 checks. |
| `api.py`, `language.py`, `translation.py` | The language service — `/health`, `/detect`, `/translate`. |
| `smoke_test.py` | Four end-to-end rehearsals: `<url>`, `incident`, `suppressed`, `escalation`. |
| `eval_trigger.py` | The gate. Runs every suite as a subprocess, measures, rewrites `EVAL-TRIGGER.md`. |
| `eval_accuracy.py` | Real accuracy against a labelled dataset, with the alignment check above. |
| `rank_clips.py` | Ranks demo footage by whether it would actually fire the trigger. |

## Running it for real

```
pip install -r requirements-trigger.txt        # pulls torch, ~2 GB

python yolo_trigger.py doctor                  # camera, model, API, audio

uvicorn incident_api:app --port 8001           # terminal 1

python yolo_trigger.py camera --zone BAY-3 \
    --api http://127.0.0.1:8001 \
    --source demo-01-best-13386074.mp4         # terminal 2
```

`--source` takes a camera index, a video file, or a still image. Drop it
to use the default camera.

The demo clips are named best-to-worst by `rank_clips.py`, which scored
them with the real detector rather than by eye. Picking footage by
watching it does not work: plenty of construction video shows everyone
correctly helmeted, which the model reads as compliance and the trigger
correctly ignores.

## Configuration

Copy `env.example` to `.env`. **Nothing in it is required** — the
incident service is deterministic and offline, and the trigger runs with
no API keys at all.

| Variable | Effect |
|---|---|
| `HAZARDWATCH_HITS` / `HAZARDWATCH_WINDOW` | The K-of-M gate. Defaults 3 and 8. |
| `HAZARDWATCH_CONF` | Confidence floor. Default 0.45. |
| `HAZARDWATCH_TIMEOUT` | Client timeout for `/incident`. Default **90s** — see below. |
| `HAZARDWATCH_TIMEOUT_COOLDOWN` | Extra gate hold after a timeout. Default 30s. |
| `CORS_ORIGINS` | Frontend origin. Unset allows any, which is right until the frontend has a URL. |
| `FEATHERLESS_API_KEY` | Enables `POST /incident/brief`, and nothing else. |

### One `/incident` at a time

`/incident` is called **serially, never concurrently.** Measured against
the deployed service: six requests fired back to back had **five
rejected with 429**.

The cause is not the request rate in the abstract. An abandoned request
keeps consuming the provider's rate limit server-side after the client
has given up waiting on it, and there is no way to cancel it once sent
— so giving up early costs both the incident *and* the quota. The only
pacing that works is to never have a second request in flight.

Three places enforce that:

| Where | How |
|---|---|
| `post_incident()` | A process-wide lock held for the whole round trip, released only when the call fully returns — success, 503, or client timeout. |
| `fire_incident_async()` | The camera's POSTs go on the single downstream worker, so they are serial *and* the loop never waits on one. |
| After a timeout | The gate is held a further 30s. A 200 or a 503 means the server is done and the quota is free; a *timeout* means the opposite — we hung up, it is still running, still consuming. Releasing there hands the next caller a slot that is not free. |
| The kiosk UI | A promise chain, not a boolean flag — React state lands a render late, so `disabled` alone still lets a fast double-click put two on the wire. Queued presses show **"Processing previous alert…"**. |

The client timeout is **90 seconds**, matching the worst case to plan
around. That is only safe because the camera no longer blocks on it:
inline, a frame with three violations would have stalled the loop for
four and a half minutes — the exact failure this project exists to
prevent. Verified against a stub that sleeps 3s per call: peak
concurrency 1, and the loop finished all 90 frames while the third
incident was still in flight.

That fourth row is the one worth reading twice. "Wait for success, 503,
or client timeout" is not sufficient on its own — the timeout case is
exactly the one where the server has *not* finished with us, and it is
the case the 429s were traced to. The right hold length is unknowable
from this side, so 30s is a tunable hedge, not a measurement.

**The lock is process-local, and that is a real limit.** Two bays
watched by two `yolo_trigger` processes do not queue behind each other.
One process watching several zones does. Anything wider has to be
serialised on the service side.

Note that this repo's own `/incident` is deterministic and calls no
model, so it cannot 429 — unless `INCIDENT_LLM=1` is set, which is off
by default. If you are hitting rate limits on the safety path, check
that variable before reaching for the queue.

### About Featherless

Featherless is called in exactly one place: `POST /incident/brief`,
which writes a shift-handover note for the safety log and runs only when
an operator presses a button. The autonomous safety path never touches a
model.

That is a licensing decision, not a performance one. Featherless
Chat/Premium plans are sold for human-driven interactive use and
**exclude automation**; a 429 from a Chat-tier key is the plan refusing
automated traffic, not a rate limit, and a larger Chat tier does not fix
it.

With no key set, `POST /incident` still returns **200** and
`POST /incident/brief` returns **503** with a message stating that the
incident response is unaffected. The brief failing cannot degrade the
safety path.

## Deployment

See [DEPLOY.md](DEPLOY.md). Two things there will cost you an hour if
you skip them: the Docker command must point at `incident_api:app` —
not `api:app`, which serves a different service and has no `/incident`
— and `VITE_API_BASE_URL` must be set **before** the frontend's first
build, because Vite inlines it at build time.

The frontend shows a red `DEMO FALLBACK` badge when it is not talking to
the backend. That badge is the fastest deployment diagnostic here: no
badge means the response is genuinely coming from the deployed service.

## What this does not do

Stated so nothing above reads as more than it is.

- **The accuracy numbers are not your bay.** They come from a
  construction-site dataset. Different lighting, different angles,
  different clothing. Treat them as an upper bound.
- **The model's training data is unknown to us.** These are public
  weights. If they overlap the test split the figures are optimistic,
  and that cannot be verified from a checkpoint alone.
- **No SMS was ever sent.** The dispatch decision, the per-channel
  formatting and the delivery report are real; only the last hop is a
  stub. Swapping in Twilio means changing a URL and a transport, not the
  logic.
- **Nothing here is legal advice.** The citation table points a human at
  the right part of the rulebook. It is a starting reference, not a
  compliance determination.
- **Nothing is measured over hours.** Every figure comes from a short
  run. Nothing here says what happens after a day of watching a bay.
